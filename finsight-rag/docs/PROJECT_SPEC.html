FinSight RAG
Grounded Q&A over SEC financial filings

An end-to-end, production-style Retrieval-Augmented Generation system that answers analyst questions about public-company 10-K / 10-Q filings with page-level citations. It runs fully on a MacBook with local embeddings and a local LLM, and switches to Claude by changing one config value.

Builds on the hybrid-retrieval experiment (BM25 + dense + RRF + rerank on FiQA) in the parent folder. This project is fully independent: its own package, data, indexes, utilities, tests and docs.

0One-page summary

Problem

Analysts spend hours searching 100–300-page filings for one number or risk statement. Generic LLMs make up figures. We need answers that cite the exact page, and that say "not found" when the filings don't contain the answer.

Data

FinanceBench (open-source sample): 150 expert-written questions with gold answers and the gold evidence page, over real SEC filings (PDFs). Optional second benchmark: MultiHop-RAG (609 news articles, 2,556 queries).

Showcase

Naive → hybrid → reranked → query-transformed → corrective → agentic RAG, all scored against the same ground truth, so every technique has to show a measured gain.

Runs on

A MacBook with Apple Silicon and 16 GB RAM (recommended). Local: bge-small embeddings, bge-reranker, an Ollama 7–8B model, Qdrant. No paid key needed.

Cloud switch

LLM_PROVIDER=anthropic uses Claude for generation, and Claude Haiku as an optional evaluation judge. The keys live in .env and are never committed.

Production shape

Typed Python package, a config-driven CLI, a FastAPI service, a Streamlit demo UI, Docker Compose, tests, GitHub Actions CI with an eval regression gate, and ADRs.

2Problem statement

Problem. Financial analysts, auditors and investors need fast, trustworthy answers to questions such as "What was 3M's FY2018 capital expenditure?" or "Did Adobe's operating margin improve between FY2015 and FY2017?". The answers sit in long, table-heavy SEC filings. Keyword search misses paraphrases, and LLMs alone invent numbers. An error in a financial answer costs real money.

Users & jobs-to-be-done

  • Analysts: look up a metric for a company and year
  • Analysts: compare a metric across years
  • Auditors: find the exact page that supports a claim
  • Everyone: be told plainly when the filings don't answer the question

Requirements

  • Grounded: every claim cites [company · doc · page]
  • Abstains: says "not in the provided filings" rather than guessing
  • Filterable: narrows the search by company, year and doc type
  • Local-first: runs offline on a laptop, with the cloud LLM optional
  • Measurable: every change is scored on a fixed eval set

Success metrics (targets to confirm after the Phase 5 baseline)

MetricWhat it measuresHow
Page Recall@10Did the gold evidence page appear in the top-10 retrieved chunks?Compare chunk page metadata with the FinanceBench evidence page
MRR / NDCG@10How high was the gold page ranked?Same ground truth (continues the experiment's metric)
Answer correctnessDoes the answer match the gold answer?Numeric tolerance match plus an LLM judge for text answers
FaithfulnessIs every claim supported by the cited chunks?LLM judge per claim
Citation precisionDo the cited pages actually contain the support?Cited page vs. evidence page
p50 / p95 latencyTime spent in each stagePer-stage timers in logs

No target numbers are promised up front. We measure the naive baseline first, then report how much each technique changes the score. That before-and-after table is the strongest interview artifact.

3Dataset

Primary: FinanceBench (open-source sample) — recommended

What it is

  • 150 expert-annotated Q&A pairs about publicly listed companies (Patronus AI, 2023, arXiv 2311.11944)
  • Each row has: question, gold answer, company, document name, and the evidence text and page number (0-based, verified against PyMuPDF)
  • Question types: 50 metrics-generated, 50 domain-relevant, 50 novel-generated
  • The source documents are real SEC filings (10-K, 10-Q, 8-K, earnings releases), shipped as PDFs in the GitHub repo
  • Q&A on Hugging Face (PatronusAI/financebench); PDFs on GitHub (patronus-ai/financebench/pdfs)

Why it fits this project

  • Continuity: the same finance domain as the FiQA experiment
  • Long PDFs with tables: chunking and parsing are real problems here, not toy ones
  • Page-level ground truth: lets us score retrieval, not only the final answer
  • Laptop-sized: the 150 questions reference 84 filings (64 10-K, 8 10-Q, 6 8-K, 6 earnings releases), about 165 MB of PDFs out of the repo's 368 files (~705 MB). That is "a bit large" but fits comfortably on a MacBook.
  • Realistic question types: metric lookup, multi-year reasoning, and calculations
License: FinanceBench is CC-BY-NC-4.0 (non-commercial use only). That is fine for a portfolio or learning project. Say so in the README and don't redistribute the PDFs in your repo: the download script fetches them.

Secondary (Phase 7): MultiHop-RAG

609 news articles (Sep–Dec 2023, average about 2K tokens) and 2,556 queries of four types: inference, comparison, temporal, and null (unanswerable, 301 of them). Most queries need 2–4 pieces of evidence. It is the right benchmark for showing query decomposition, agentic multi-hop retrieval, and refusal on unanswerable questions. It is small (a few MB) and loads through the same loader interface, which also shows the code works on more than one corpus.

EmbeddingsBAAI/bge-small-en-v1.5 (384-dim) via sentence-transformers on MPS—Much stronger retrieval than MiniLM at similar speed. 384 dimensions keep the Qdrant index small. Swap to bge-base (768-dim) as an experiment.

PDF parsingpymupdf (fast, page-accurate)—Fast across thousands of pages. Note that it is AGPL-licensed; pypdf (BSD) is the fallback. Record the choice in an ADR.
Vector DBQdrant (embedded mode for dev, Docker for the service)Qdrant CloudMetadata filters, persistence, a simple API, widely known in interviews. One code path for local and Docker.
Sparse indexbm25s—You already know it from the experiment. Fast, and saves to disk.
App layerFastAPI, typer CLI, pydantic-settings, Streamlit—Standard Python production stack with typed config.

Why no LangChain or LlamaIndex? Retrieval, fusion, prompting and evaluation are written by hand, around small interfaces (Retriever, Reranker, LLM, Chunker). That proves you understand each part, and a framework could still be added behind those interfaces later. This is a deliberate choice, recorded as an ADR.
Claude API notes for the code: use the official anthropic Python SDK and read ANTHROPIC_API_KEY from the environment. Current Claude models reject the temperature, top_p and top_k parameters, so don't send them. Control depth with output_config={"effort": "low"} for the judge. Check stop_reason (including "refusal") before reading the answer text.

Key design principles

Interfaces + registries

Every stage is a small ABC (Chunker, Retriever, Reranker, LLM). Implementations register by name, so a YAML file chooses the pipeline. A new technique is a new class plus one config line.

One pipeline, three callers

The CLI, the API and the eval runner all build the same RAGPipeline object from config, so the scores you report match what the API actually serves.

Idempotent indexing

A manifest stores hashes of the corpus, chunker config and embedding model. Re-running skips the work if nothing changed, and rebuilds if anything did.

No side effects at import

Unlike the numbered experiment scripts, no module loads models or data when imported. Expensive objects are created lazily and cached in a dependency container.

9Roadmap: step by step

Twelve phases. Each one ends with something runnable, a commit or PR, and a "done when" check. Click a phase to expand it. Time estimates assume evenings and weekends.

Build

  • config.py (pydantic-settings loading YAML + env), observability/logging.py (JSON logs), schemas.py
  • Makefile, pre-commit, .env.example, .gitignore for data, indexes and .env
  • CI workflow skeleton: lint, type-check, unit tests
Done when
  • make lint test passes locally and in CI; finsight --help works
You learn / can explain
  • src layout, typed config, why no work happens at import, and dependency injection
P1Data acquisition & exploration~1 day
Build
  • data/download.py: fetch the FinanceBench JSONL from Hugging Face, then fetch only the PDFs it references from GitHub. Skip files already downloaded, check them, and print the counts.
  • data/financebench.py: load rows into EvalRecord (question, answer, doc, evidence page)
  • notebooks/01_explore_financebench.ipynb: question types, companies, pages per document, evidence page positions
  • docs/data_card.md: source, license, size, known issues
Done when
  • finsight download is repeatable, and the data card states the real document, page and question counts
P2Ingestion: PDF → clean pages + metadata~2 days
Build
  • pdf_parser.py: per-page text with 1-indexed page numbers that match the FinanceBench evidence pages
  • cleaner.py: strip repeated headers and footers, fix hyphenation, normalize whitespace
  • tables.py: keep table rows intact (pipe-separated text) so numbers stay next to their labels

  • Output: processed/pages.parquet
Done when
  • For a sample of 20 questions, the gold evidence text is found on the parsed page with that page number (an automated test)
Interview point
  • "Garbage in, garbage out": parsing quality caps how good retrieval can ever be, and this test proves our parsing is correct
P3Chunking strategies~2 days
Build
  • Chunker ABC plus a registry; implementations: fixed (token windows with overlap), recursive (paragraph → sentence → token), page_aware (never crosses a page boundary, so citations are clean), parent_child (small chunks for search, the parent section for the LLM)
  • Every chunk carries doc_id, company, fy, doc_type, page_start, page_end, chunk_id, parent_id
  • notebooks/02_chunking_analysis.ipynb: token-length histograms and chunk count per strategy
Done when
  • Unit tests cover the overlap, page-boundary and parent-link invariants; finsight ingest --chunker X writes chunks/X.parquet
P4Embedding & indexing~2 days
Build
  • Embedder on MPS with batching; cache keyed by sha256(model + text), so re-chunking only embeds new text
  • qdrant_store.py: one collection per (chunker, model); payload indexes on company and fiscal year; batched upserts
  • bm25_store.py: a bm25s index per chunker, with chunk IDs kept in the same order
  • manifest.py: hashes of corpus, config and model, to skip or rebuild
Done when
  • finsight index finishes on the full corpus on your Mac; the timing and index size are written to the README
P5Retrieval + retrieval evaluation (baseline)~3 days
Build
  • DenseRetriever, SparseRetriever, HybridRetriever (RRF), filters.py (rule-based company and year extraction first), LocalReranker, with Cohere as an optional reranker
  • retrieval_metrics.py: page Recall@k, MRR, NDCG@10. A hit means a retrieved chunk overlaps the gold page.
  • finsight eval --stage retrieval --config experiments/retrieval_ablation.yaml writes results/*.md
Done when
  • The first results table exists: {dense, BM25, hybrid, hybrid+filter, hybrid+rerank} × {4 chunkers}, scored on all 150 queries
Interview point
  • Show the ablation table: which stage helps on which question type, and the cost in latency
P6Grounded generation (local + Claude)~3 days
Build
  • LLM ABC with generate() and stream(); OllamaLLM over its HTTP API; AnthropicLLM via the official SDK (retries, refusal handling, token usage logged)
  • prompts/answer.md: numbered context blocks [1] (3M · 10-K 2018 · p.45). Rules: answer only from the context, cite as [n], show calculations, otherwise give the abstain phrase.
  • citations.py: parse the citations, drop any that point to context not provided, and mark the answer "unsupported" if it cites nothing
  • NaivePipeline and HybridRerankPipeline built from config
Done when
  • finsight query "What was 3M's FY2018 capex?" returns an answer with page citations, on both providers, with a one-flag switch
P7Advanced RAG techniques~4–5 days
Build
  • Query transforms: multi-query (3 paraphrases fused with RRF), HyDE (embed a hypothetical answer), decomposition (sub-questions for multi-year comparisons)
  • Contextual chunk headers: prepend "Company · FY · doc · section" to each chunk before embedding. The cheap version needs no LLM; the full version uses a local LLM to write a one-line summary per chunk.
  • CorrectiveRAG: an LLM or reranker-score check decides whether the evidence is enough. If not, rewrite the query and retry once, then abstain.
  • AgenticRAG: a tool loop (search(query, filters), read_chunk(id), answer()) with a step limit, evaluated on MultiHop-RAG including the null queries
  • Add a multihop.py loader; the same eval runner works for both datasets
Done when
  • results/advanced.md compares each technique with the P5/P6 baseline and shows the latency and LLM-call cost of each
P8End-to-end evaluation harness~3 days
Build
  • generation_metrics.py: numeric match (parse numbers, compare within a relative tolerance), exact or contained match, abstention accuracy
  • judge.py: LLM-as-judge for correctness and faithfulness against a fixed rubric, with JSON output validated by pydantic. Cache judge results on disk so re-runs are free.
  • runner.py: run an experiment matrix from YAML, save one JSON line per question (inputs, retrieved IDs, answer, scores, timings, tokens)
  • report.py: Markdown tables, a per-question-type breakdown, a failure gallery (the 10 worst cases with their retrieved chunks)
  • CI regression gate: a 10-question fixture with retrieval only (no LLM) runs in CI and fails if Recall@10 drops below a stored threshold
Done when
  • make eval produces a full report; judge agreement is spot-checked by hand on 20 answers, and the result is written down
P9Serving: API + demo UI~2 days
Build
  • FastAPI: GET /health, GET /ready (indexes loaded), POST /query (pipeline name, filters, top_k), POST /query/stream (Server-Sent Events)
  • The response includes the answer, citations with snippet and page, per-stage timings, token usage and the request ID
  • Streamlit UI: question box, provider and pipeline dropdowns, answer with clickable citations, and an expandable "under the hood" panel (BM25 vs. dense vs. fused vs. reranked lists with scores). This panel is what you'll show interviewers.
Done when
  • The API integration tests pass, and a 60-second demo GIF is in the README
P10Production hardening & deployment~2–3 days
Build
  • Multi-stage Dockerfile (uv, non-root user, models pre-downloaded into the image or a mounted volume); docker-compose runs api, qdrant and ui, with Ollama reached at host.docker.internal
  • Timeouts, retries and fallbacks: if Claude fails, fall back to Ollama; if the reranker fails, use the RRF order
  • Caching: query-embedding LRU cache and a cache for answers to identical questions
  • Security: secrets only from the environment, input length limits, treat retrieved text as data (a prompt-injection note in the system prompt), basic rate limiting
  • docs/runbook.md: how to rebuild indexes, rotate keys and debug a bad answer
Done when
  • docker compose up on a fresh clone (plus make data index) serves answers
P11Documentation & showcase~2 days

10Evaluation plan

Experiment matrix (one variable at a time)

  • E1 Chunking: 4 strategies × 2 sizes (256 / 512 tokens), with hybrid retrieval held fixed
  • E2 Retrieval: dense, BM25, hybrid, + metadata filter, + reranker
  • E3 Query transforms: none, multi-query, HyDE, decomposition
  • E4 Generator: Ollama 7B vs. Claude on the best retrieval setup
  • E5 Pipelines: naive vs. hybrid_rerank vs. corrective vs. agentic
  • E6 Generalization: best pipeline on MultiHop-RAG, including null queries

Rigor

  • Fixed seeds; the resolved config and its hash are stored with every result
  • Results broken down by question type, not only the overall average
  • Judge validated against 20 hand labels; disagreements written up
  • Retrieval metrics are free (no LLM), so run them often; judge runs are cached
  • Report the cost of each gain: added latency and extra LLM calls

11Production readiness checklist

Code quality

  • Type hints everywhere, mypy run in CI
  • ruff lint and format
  • Unit and integration tests, with coverage reported
  • No side effects at import

Reproducibility

  • uv.lock pins dependencies
  • Config hash in every result
  • Index manifest
  • Data downloaded by script, never committed

Reliability

  • Timeouts and retries on every external call
  • LLM and reranker fallbacks
  • Health and readiness endpoints
  • Graceful abstain

Observability

  • JSON logs with a request ID
  • Per-stage latency
  • Token and cost tracking per request
  • Retrieved IDs logged for debugging

Security

  • Secrets only from the environment; .env gitignored
  • Prompt-injection guard in the system prompt
  • Input size limits
  • Non-root container

Documentation

  • README quickstart
  • Architecture doc and ADRs
  • Data card and license
  • Runbook and interview guide

12Git & CI workflow

  • Branch per phase: feat/p2-ingestion → PR into main → CI must pass → squash merge. Small PRs with clear descriptions read well on GitHub.
  • Conventional commits: feat(chunking): add parent-child chunker, test(retrieval): RRF tie handling, docs(adr): vector store choice
  • Automation on every push: GitHub Actions runs ruff, mypy, unit tests, integration tests on the fixture corpus, and the retrieval regression gate. Pushing is how the project "deploys" its quality checks.
  • Release tags: v0.1 (P6, basic RAG), v0.2 (P8, full eval), v1.0 (P11, showcase). Each tag links to its results report.
  • Never committed: .env, data/, indexes/, model weights

13Interview narrative

30-second pitch: "I first rebuilt hybrid retrieval on FiQA to understand BM25, dense retrieval, RRF and reranking in isolation. Then I built FinSight RAG, a production-style system over real SEC filings. It parses long PDFs, compares four chunking strategies, runs hybrid retrieval with metadata filters and a local reranker, and generates cited answers with a local LLM or Claude. It also abstains when the evidence isn't there. Every technique is measured on FinanceBench against page-level ground truth, and CI blocks retrieval regressions."
Likely questionWhere your answer lives
Why hybrid rather than dense only?The E2 table: BM25 wins on exact tickers, line-item names and years; dense wins on paraphrase; RRF combines ranks without needing to calibrate scores
How did you choose chunk size and strategy?The E1 table and ADR-0003; page_aware chunks give clean citations
How do you know it works?The P8 harness: retrieval and generation metrics, a hand-validated judge, the failure gallery
How do you prevent hallucination?Grounding prompt, citation validation, CRAG grading, abstention accuracy metric
Latency vs. quality trade-off?Per-stage timings; the reranker's cost vs. its gain; when to skip query transforms
How would you scale to 1M documents?Qdrant sharding and HNSW tuning, async ingestion workers, embedding batch jobs, a cache layer, approximate filters
Why not LangChain?ADR-0002: transparency and testability; the interfaces would let you add it later

14Risks & mitigations
